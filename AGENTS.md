# tennis_book — правила работы

## Контекст и первый вход

Это существующий сервис теннисного центра из https://github.com/numinga27/tennis_book . Не создавать новый репозиторий, не менять его владельца/visibility и не заменять исходный продукт новой архитектурой.

Читать README.md, docs/workflow/CURRENT.md, docs/product/BRIEF.md и docs/workflow/TEAM.md. Локальный реестр канонических чатов — .codex-local/project-chats.json; он не публикуется в публичном Git. Если реестра нет, уточнить организационный checkpoint, не создавать дубликаты чатов.

Существующий код расположен в tennis_booking/: Django, booking, users, payment, шаблоны и миграции. Фактическая работоспособность ещё не проверена. Организация чатов не разрешает переписывать сайт, мигрировать данные или автоматически создавать мобильное приложение. Сначала воспроизвести существующий запуск на изолированных тестовых данных.

## Роли и параллельность

- Канонический оркестратор ведёт очередь, зависимости и приёмку; другие роли не организуют собственные независимые проекты.
- Все оркестраторы Astra medium, сложная диагностика/архитектура — high. Сложные исполнители Astra; простые ограниченные задачи Terra/Sol только по глобальному правилу. Luna/Fast запрещены. 401/429 не исправлять сменой модели.
- Глобально максимум две обычные исполнительные задачи с учётом других проектов. Шесть созданных ролей не означают шесть работающих исполнителей. При организационном создании чаты только подтверждают роль и завершают turn без работы.
- У задачи должны быть результат, разрешённые файлы, критерий приёмки, evidence и следующий шаг. Один writer на пересекающиеся файлы; контракты backend/сайта/мобильного клиента согласуются перед изменением.
- Сначала Git status, CURRENT.md и последний evidence. Не повторять принятые шаги, генерацию или внешние записи без readback. Сохранять dirty/untracked данные.
- Не создавать дополнительные чаты, подагентов и расписания без полномочий. Пользовательские уточнения учитывать в каноническом чате, без копий проекта.

## Безопасность исходного состояния

В исходном публичном Git уже присутствуют db.sqlite3, db.json и Python __pycache__. Базы не читать и не публиковать в отчётах до выяснения, синтетические ли данные; не использовать их для миграций/тестов, не удалять. Проверку возможной утечки и ротацию согласовывать отдельно; исторические секреты не цитировать и не копировать. Настройки DEBUG/SECRET_KEY требуют аудита перед публикацией, но организационный этап их не меняет.

Не устанавливать зависимости из догадок и не выбирать версию Django по заголовкам pyc. Сначала определить зависимости/совместимость, затем закрепить воспроизводимый dev toolchain. Новые тестовые данные только вымышленные и отдельно от исходных баз.

Этот репозиторий публичный. Не добавлять секреты, реальные данные клиентов, внутренние chat ID, логи с персональными сведениями и локальные реестры. Для организационных изменений использовать отдельную ветку; main/историю/старые tracked файлы не переписывать. Проверять точный remote и права перед push.

## Gates и качество

Никаких production deployment, платных аккаунтов, реальных платежей, возвратов, сообщений клиентам, записей в рабочую БД или управления магазинами из команды об организации. Существование payment-модели не доказывает рабочий эквайринг. Сначала проверить платежные сценарии в разрешённой sandbox-среде и отдельно фиксировать готовность реальных интеграций.

Мобильный формат (Android/iOS/PWA/native), дизайн и стек не утверждены; сначала подтвердить цель и переиспользование backend, не обещать готовое приложение. Перед сборками проверять C:; ниже80ГиБ не запускать второстепенные тяжёлые сборки без конкретного исключения, ниже50ГиБ не делать новые экспорты/резервные копии. Малый организационный clone не является разрешением на toolchain/downloads.

Проверять бронирования, пересечения времени, конкуренцию запросов, права пользователя/администратора, стоимость и переходы статусов. Это список направлений будущей проверки, не утверждение найденных дефектов. QA не меняет приложение параллельно разработчику. Mock, локальный запуск, sandbox и production — разные статусы.

После каждого проверенного этапа обновлять короткий CURRENT.md: выполнено, evidence, не проверено, блокер, следующий шаг. Не заявлять готовность по наличию файлов или активному статусу чата.
